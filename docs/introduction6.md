**第六章 兼容性、特性系统与最佳实践**

---

### 6.1 标准 API 与可选特性的边界

满月平台的兼容性策略建立在两个明确的层次之上：

**标准 API（最大公约数）**

- 只收录主流平台都具备**类似行为**的接口。
- 使用这些 API 编写的插件，理论上可以在所有被第三方库支持的平台上运行。
- 这是满月平台追求“一次编写，多平台运行”的基础。

**可选特性（Features）**

- 对应部分平台才拥有的能力（例如特定的数据库支持、WebSocket、插件间事件通信等）。
- 在 `fmplib` 的 `FeaturesIndex.ts` 中通过 `//featureName>> ... //featureName<<` 标记。
- 插件必须在 `plugin.json` 的 `features` 数组中**显式声明**才会启用。
- 构建时未声明的特性会被裁剪为 `undefined`。

**边界原则**：

- 标准 API 保证基础兼容性。
- 可选特性提供能力扩展，但把兼容性选择权交给插件作者。
- 满月平台本身**不强制**任何可选特性，也不保证所有平台都能实现所有特性。

---

### 6.2 使用可选特性时的兼容性代价

启用可选特性会带来明确的代价：

1. **平台覆盖面缩小**  
   插件可能无法在不支持该特性的加载器上运行。

2. **依赖增加**  
   若特性映射到外部 npm 包，产物会携带额外依赖；若平台声明为 `internal`，则依赖平台自身实现。

3. **测试负担上升**  
   需要针对启用了特性的平台单独验证行为。

**建议决策流程**：

- 能用标准 API 实现的功能，优先使用标准 API。
- 只有在功能不可或缺、且能接受兼容性损失时，才启用可选特性。
- 在插件文档中明确列出“需要哪些特性、支持哪些平台”，方便服主判断。

---

### 6.3 跨平台测试建议

1. **至少测试两个差异较大的平台**  
   例如一个偏 Node.js 环境的平台（如部分 LLSE / BDSX）和一个差异明显的其他平台，有助于发现实现差异。

2. **区分标准功能与可选特性**  
   - 关闭所有 `features` 进行一次完整测试（验证最大兼容路径）。
   - 再针对每个启用的特性单独测试。

3. **关注同步 / 异步语义**  
   在不同平台上验证事件拦截、主线程相关操作是否符合预期。

4. **检查数据路径与权限**  
   确认 `data_path` 在不同平台上被正确解析，权限节点行为一致。

5. **使用 FullMoonTester 类项目**  
   社区已有专门测试 fmplib 全部 API 的项目，可作为回归测试参考。

6. **产物验证**  
   构建后检查各平台目录下的文件是否完整、`package.json`（如有）依赖是否被正确清洗、未启用特性是否已变为 `undefined`。

### 6.4 常见陷阱与反模式

| 陷阱 | 说明 | 正确做法 |
|------|------|----------|
| 直接引用 `lib` 内部文件 | 如 `import ... from "../lib/Game/Player.js"` | 始终从 `../lib/index.js` 导入 |
| 把开发时的 `lib` 当作运行时实现 | 空壳中的代码不会出现在最终产物 | 只依赖类型与注释，逻辑完全由第三方库提供 |
| 忽略同步 / 异步定义 | 把同步 API 当 Promise 使用，或反之 | 严格遵守契约中相应函数定义是否被async修饰 |
| 过度使用可选特性 | 导致插件只能在极少数平台运行 | 能不用就不用，必须用时在文档中明确说明 |
| 在业务代码中硬编码平台差异 | 破坏“一次编写”的目标 | 把平台差异留给第三方库处理 |
| 修改 `lib` 目录内容后期望生效 | 构建时 `lib` 会被替换 | 需要修改实现时，应编写或修改第三方库 |
| 不配置 `priorities.default` | 构建系统找不到任何实现库 | 至少配置一个可用的第三方库（通常是 LNSDK） |
| 钩子滥用 | 把本应在适配器中实现的逻辑放到 `before/after_compile.js` | 钩子仅用于编译期特殊需求 |

### 6.5 对 AI Agent / Vibecoding 的特殊注意事项

Vibecoding 场景下，AI 容易用“常规框架思维”去理解满月平台，从而生成错误代码。请特别注意以下约束：

1. **这是编译期替换，不是运行时多态**  
   不要生成动态 `require`、代理对象或运行时平台检测逻辑来“模拟”多平台。正确模型是：源码只面对契约，构建时物理替换实现。

2. **`lib/index.ts` 是唯一公共入口**  
   生成的 import 必须指向 `../lib/index.js`（或项目中对应的路径）。禁止直接引用内部模块路径。

3. **空壳不是实现**  
   开发时看到的 `lib` 几乎全是空实现。生成业务代码时，不要依赖其中任何运行时逻辑。

4. **不要发明平台专有 API**  
   只使用 fmplib 已定义的接口。需要额外能力时，应通过可选特性或建议用户编写第三方库扩展，而不是在插件源码中直接调用加载器私有 API。

5. **`plugin.json` 与 `priorities` 必须正确**  
   生成项目时务必包含有效的 `priorities.default`，否则构建会失败。

6. **特性声明要诚实**  
   如果代码使用了某个可选特性，必须在 `features` 数组中声明，否则构建后会得到 `undefined`。

7. **尊重职责边界**  
   - 事件系统、热重载、具体加载逻辑 → 第三方库或加载器负责。
   - 入口形式与构建流程 → 满月平台负责。
   - 业务逻辑 → 插件负责。

8. **生成第三方库时**  
   必须同时提供 `fmplib.json`、各平台的 `platform.json`、符合约定的 `lib/index.ts` 和 `FeaturesIndex.ts` 标记。缺少这些文件的库无法被构建系统正确识别。

---

### 6.6 本章小结

兼容性是满月平台的核心价值之一，但它不是无条件的：

- 标准 API 提供最大公约数，保证基础跨平台能力。
- 可选特性提供扩展能力，同时把兼容性选择权交给开发者。
- 良好的测试习惯、避免常见陷阱、对 AI 生成代码保持契约意识，是产出高质量、可维护插件的关键。

只要坚持“面向契约编程 + 构建时替换”的核心模型，就能在享受 TypeScript 开发体验的同时，真正实现多平台分发。
