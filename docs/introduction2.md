**第二章 架构分层与组件职责**

---

### 2.1 整体架构关系图

满月平台采用**自上而下**的分层设计，逻辑流向如下：

| 层级 | 角色 | 核心职责 |
|------|------|----------|
| **fullmoonplatform** | 概念定义者 + 工具提供者 | 定义“满月插件”规范、入口规范、目录结构；提供 `build.ts` / `generate.ts` 等构建工具 |
| ↓（制定规范与构建规则） |
| **fmplib** | 参考契约 | 提供纯类型定义与接口边界；开发时类型提示与最大 API 范围；少量供构建工具使用的参考实现 |
| ↓（契约被实现） |
| **LNSDK 及其他第三方库** | 连接现实的适配器 | 实现 `fmplib` 定义的接口；采用适配器模式对接真实加载器；编译期被“偷梁换柱”替换进插件 |
| ↓（编译期绑定） |
| **真实宿主环境** | 运行目标 | LiteLoaderBDS / LeviLamina / BDSX / PNX-JS / …… |

开发者视角下的依赖关系非常简单：

- 开发时：只依赖 `fmplib`（或自写的契约层）。
- 构建时：由 `fullmoonplatform` 的 `build.ts` 负责将第三方库的实现注入。
- 运行时：产物已经绑定到具体平台的实现，直接调用底层 API。

---

### 2.2 fullmoonplatform：概念定义者与工具提供者

**定位**：一切的开端。它定义“满月平台”这个抽象概念，并提供让概念落地的工具链。

**核心职责**：

1. **概念与规范定义**
   - 规定插件源码必须提供的入口形式。
   - 规定项目目录结构（`src`、`lib`、`libs`、`plugin.json` 等）。
   - 规定第三方库必须遵循的格式（`fmplib.json`、`platform.json`、目录布局等）。
   - **不负责**事件系统的具体设计、热重载逻辑、具体 API 的实现。这些属于第三方库或加载器的职责。

2. **构建工具**
   - `build.ts`：核心构建脚本，负责多平台并行编译、库替换、特性裁剪、依赖清洗。
   - `generate.ts`：主要用于维护 fmplib 自身的部分代码生成，**不是**给插件开发者日常使用的工具。

3. **约束边界**
   - 满月平台本身**不强制**使用 fmplib 作为契约层。开发者若有特殊需求，可以自行编写契约。
   - 它只要求最终产物符合入口与构建规范，能够被目标加载器正确加载。

**一句话总结**：fullmoonplatform 回答的是“满月插件应该长什么样、应该怎么被构建”，而不是“具体怎么操作游戏对象”。

---

### 2.3 fmplib：参考契约与接口边界

**定位**：开发者编写插件时直接面对的契约库。

**核心职责**：

1. **接口定义**
   - 几乎所有类、函数、方法都以空实现或类型定义的形式存在。
   - 通过 `index.ts` 统一导出所有公开 API。插件源码**必须**从 `lib/index.js`（或对应路径）导入，而不是直接引用内部文件。
   - 定义了标准化的数据结构（如 `Player`、`Item`、`Location`、`NBT` 等）。

2. **同步 / 异步策略**
   - 与游戏主线程拦截、CPU 密集型逻辑相关的 API 定义为**同步**。
   - 其余文件、网络、UI 相关操作定义为**异步**。
   - 策略完全由“这个 API 的目的是什么”决定，而不是统一强制异步。

3. **参考实现的有限用途**
   - 少量基础 API 的实现仅供 `fullmoonplatform` 的构建工具（`generate.ts` / `build.ts`）使用，或作为示例。
   - 它们**不是**运行时依赖。

4. **最大 API 边界**
   - fmplib 划定了“满月平台认可的接口范围”。超出这个范围的模块，不被认为是满月平台的一部分。

**重要说明**：  
fmplib 是“空壳”。开发时它提供完美的类型提示与注释；编译时它会被第三方库的真实实现物理替换。

---

### 2.4 LNSDK 及其他第三方库：连接现实的适配器

**定位**：把抽象契约连接到真实服务端加载器的实现者。

**核心职责**：

1. **实现契约**
   - 必须实现 fmplib 定义的接口，保证插件调用这些接口时，在真实服务端上产生正确行为。
   - 目录结构与导出方式应尽量与 fmplib 保持兼容（至少 `index.ts` 导出的接口要能正常工作）。

2. **适配器模式**
   - 针对不同平台提供不同实现，放置在 `libs/<平台名>/lib` 等约定目录下。
   - 每个平台目录必须包含 `platform.json`，声明该平台的特性（是否 Node.js 环境、不支持的包、特性映射、编译选项等）。

3. **编译期被替换**
   - 第三方库是 fmplib 的**结构超集**（或至少在导出层面兼容）。
   - `build.ts` 在临时目录中把对应平台的实现复制到 `lib` 位置，完成“偷梁换柱”。

4. **非强制性**
   - LNSDK 只是当前最完整、最全面的先锋实现。
   - 开发者完全可以编写自己的第三方库来替代或补充它。
   - 满月平台只要求“行为正确”，不约束内部实现方式（JS 层转换、自建脚本引擎、原生调用等）。

5. **钩子支持**
   - 可提供 `before_compile.js` 与 `after_compile.js`，在编译前后执行自定义逻辑。

**一句话总结**：第三方库负责“把 fmplib 的调用翻译成真实加载器能听懂的语言”。

---

### 2.5 组件之间的依赖与协作边界

| 关系 | 说明 |
|------|------|
| 插件 → fmplib | 开发时依赖，用于类型提示与接口约束 |
| fullmoonplatform → fmplib | 构建工具会使用 fmplib 中少量参考实现；规范上以 fmplib 为 API 边界参考 |
| 第三方库 → fmplib | 必须实现 fmplib 定义的接口；结构上尽量兼容以便替换 |
| build.ts → 第三方库 | 根据 `priorities` 配置，将第三方库的实现注入临时编译环境 |
| 最终产物 → 宿主加载器 | 编译后的 JS 直接被加载器加载，调用的是已绑定的平台实现 |

**关键边界澄清**：

- **事件系统**：不属于 fullmoonplatform 的职责。由第三方库自行实现与管理。
- **热重载**：属于插件加载器的行为。平台与 fmplib 均不处理；第三方库可选择自行适配或增强。
- **模块加载**：fullmoonplatform 只规定“插件必须提供一个入口”。如何找到并加载这个入口，由第三方库负责引导。
- **优先级机制**：`priorities` 决定多个第三方库在编译时的层叠覆盖顺序。优先级高的库可覆盖低优先级库的同名文件，实现补丁或增强。

---

### 2.6 本章小结

满月平台的架构可以概括为三层：

1. **概念与工具层**（fullmoonplatform）—— 定义规则与构建方式。
2. **契约层**（fmplib）—— 规定插件代码应该长什么样。
3. **实现与连接层**（LNSDK 等第三方库）—— 把契约落地到真实平台。

三者职责清晰、边界明确：平台管规范与构建，契约管接口，适配器管落地。开发者只需面对契约编写代码，构建系统自动完成从抽象到具体的转换。

理解了这一章的职责划分后，第三章将深入解析 `build.ts` 如何把这些组件真正串联起来，完成多平台并行构建。
